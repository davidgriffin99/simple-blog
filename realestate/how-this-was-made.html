How This Was Made

A one-pager explaining the data model, features, and how everything connects

The Problem

Managing a portfolio of ~50 real estate and infrastructure development sites — EV charging, solar, battery storage — spread across America. Each site has different owners, vendors, permits, risks, and politics. We need a way to see the big picture, track what's blocked, learn from failures, and generate reports without drowning in spreadsheets.

The Hierarchy: Program → Project → Site

Everything is organized in three levels. This pattern comes from Sitetracker, the industry standard for multi-site infrastructure rollouts. See it live on the Hierarchy page.

Program "California EV Network 2027" ← The strategic initiative └── Project "LA Metro" ← A market or region ├── Site "Santa Monica Main St" ← A physical location ├── Site "Venice Blvd Station" └── Site "Pasadena Colorado Blvd" (dead) Program "Texas Solar Rollout 2026" └── Project "Austin Metro Solar" └── Site "Round Rock Community Solar"
LevelWhat it representsExampleKey question
ProgramA strategic initiative with a charter, budget, and sponsor"Deploy 100 EV sites across California by 2027"Why are we doing this?
ProjectA market or region within a program"LA Metro" — 20 sites targetWhat gap are we filling?
SiteA specific physical location with an address"123 Main St, Santa Monica"Where exactly?
Each level can be confirmed or exploring. A Program can exist with zero projects (still in planning). A Project can have zero sites (still scoping markets). This lets us track opportunities early, before committing.

Site Stages

Every site moves through a pipeline of stages. The Pipeline Report shows sites grouped by stage with time-in-stage tracking.

Searching → Candidate → Selected → Acquisition → Due Diligence → Entitlements → Permitting → Construction → Commissioning → Operating ↘ On Hold ↘ Dead

There is no separate "status" field — stage is the single source of truth. A dead site is simply stage: dead. This avoids the confusion of having both a status and a stage that can contradict each other.

Stage History

Every stage transition is recorded with a timestamp. This enables analytics like "permitting in California averages 4.2 months" or "how long did Santa Monica spend as a candidate?"

Health & Risk

Stages tell you where a site is. Health and risk tell you how it's doing. See the Risk Report for the full breakdown.

Lessons Learned

When a site dies or something goes wrong (or right), we capture it as a formal lesson. These are first-class records, not buried in meeting notes. See the Lessons Report.

Each lesson captures:

SituationWhat happened
What worked / didn'tSpecifics, not vague takeaways
RecommendationActionable advice for next time
Applies toWhich tech types, regions, stages this is relevant for
Example: After the Pasadena site died because the landlord backed out, we recorded: "Never start permitting without a signed LOI with penalty clause." This lesson is now linked to the dead site's post-mortem and tagged so it surfaces when starting similar acquisitions.

Decisions Log

Major decisions are recorded on each site with the rationale, who made them, and whether they're reversible. This prevents the "why did we do that?" problem six months later.

Example: Santa Monica — "Go with 8+2 charger config instead of 10 Level 2." Rationale: DC fast chargers have higher utilization. Made by Sarah. Reversible: yes.

Dead Sites & Post-Mortems

When a site is killed, it doesn't disappear. It moves to stage: dead and gets a post-mortem recording:

  • Why it died
  • Sunk cost and time invested
  • Linked lessons learned
  • Whether it could be revived, and under what conditions

Dead sites still appear in the Portfolio and Hierarchy views. Forgetting failures is how you repeat them.

Vendors

A master vendor directory tracks contractors and equipment suppliers. Each vendor has capabilities, contacts, an internal rating (1–5 stars), and an owner who manages the relationship.

When a vendor is assigned to a site, their name is stored directly on the site record (denormalized) so we can display it without extra database lookups.

How It's Built

┌──→ Dashboard (index.html) ├──→ Portfolio Report ├──→ Hierarchy View Firestore ──────────┼──→ Risk Report (5 collections) ├──→ Pipeline Report ├──→ Vendor Report └──→ Lessons Report Collections: re_programs, re_projects, re_sites, re_vendors, re_lessons

Data layer: Google Cloud Firestore (NoSQL document database). Each entity is a document in its collection. Sites store program_id and project_id for easy filtering up the hierarchy.

Reports: A Python script reads all collections, generates static HTML files. No framework, no build step. Regenerate anytime with one command.

Design decisions:

  • Stage replaces status — one field, no contradictions
  • Stage history — timestamps on every transition for duration analytics
  • Logs on every entity — append-only journals at program, project, site, and vendor level
  • Vendor names denormalized — stored on site records to avoid extra lookups
  • Risk = sum of 4 sub-scores — each 0–3, max 12, simple and consistent
  • Similarity via tags — no bidirectional links to maintain, just shared tags

Beyond Reporting: Intelligence

Static reports are table stakes. The real value is in things that actively help you make better decisions faster.

Real-Time Local Intel via SuperGrok API

An LLM continuously mines the SuperGrok API (Grok with real-time X/web access) for the latest information on every region and locality in the portfolio. SuperGrok is uniquely valuable here because it has access to real-time, hyper-local news that traditional news APIs miss — the kind of information that actually affects development timelines:

  • Wildfires, smoke advisories, extreme heat — construction crew safety, outdoor work restrictions
  • Changing city regulations — new permit requirements, zoning changes, moratoriums
  • Local political shifts — council member elections, NIMBY group formation, public hearings
  • Utility and grid issues — interconnection queue changes, transformer availability, rate changes
  • Competitor activity — other developers filing permits in your target cities
  • Community sentiment — protests, local opposition, media coverage of similar projects nearby
Example: Before a Santa Monica city council hearing, the system automatically pulls: recent battery storage protests in LA County, what arguments NIMBY groups are currently using, any new state rebate programs announced this week, and whether the council member up for re-election has made any public statements about EV infrastructure. This intel gets attached to the site record and surfaces in the Lessons and meeting prep.

Lessons Learned → Playbooks

Every dead site, every blocker, every surprise gets captured as a formal lesson. Over time, these lessons compound into something more powerful: playbooks.

A playbook is an auto-generated, continuously updated guide for a specific scenario — built from real experience across the portfolio, not generic advice:

  • "Battery storage in California" — every regulatory hurdle we've hit, what worked, what didn't, typical timelines by jurisdiction
  • "EV charging in HOA-controlled areas" — landlord negotiation lessons, common objections, successful approaches
  • "Solar on brownfield sites" — environmental assessment gotchas, remediation timelines, financing structures that worked
The flywheel: More sites → more lessons → better playbooks → faster execution on new sites → fewer dead sites → better ROI. A site that took 8 months in 2026 should take 5 months in 2027 because we've already seen every blocker and know how to handle it.

Meeting Prep Generator

Before any city council meeting, planning commission hearing, or vendor negotiation, the system auto-generates a briefing package:

  • Site status summary and recent activity
  • Real-time local news from SuperGrok (opposition, political climate, recent similar decisions)
  • Relevant lessons from similar hearings across the portfolio
  • Talking points and FAQ based on what's worked before
  • Key contacts and their known positions

Predictive Alerts

Instead of waiting for something to go wrong:

  • Permit expiry warnings — "Encroachment permit on Venice expires in 90 days, renewal takes 60"
  • Stage duration anomalies — "Santa Monica has been in permitting 45 days, average for this jurisdiction is 30"
  • Risk score trending up — "Austin political risk increased after NIMBY group formed in Cedar Park"
  • Vendor capacity — "ABC Electric is now on 4 active sites, historically quality drops above 3"

Access It From Anywhere

The data lives in one place (Firestore). The interface is whatever's convenient at the moment. This simple tracker can be accessed via:

┌──→ VS Code / Claude Code (chat interface — deep queries, analysis) ├──→ Telegram / WhatsApp (quick updates from your phone) ├──→ Slack (team alerts, channel per program) Firestore ─────────────┼──→ Email (weekly digests, forward-to-log) (single source ├──→ Website (these reports — shareable links) of truth) ├──→ PowerPoint / PDF (exec decks, board packages) └──→ Printouts (old school works too)

The key insight: you don't need to learn a new tool. Ask a question in whatever channel you're already in — Slack, a chat window, a text message — and the same data answers it. Update a site status from your phone while standing on the construction site. Generate a board deck from your laptop. Print a one-pager for a meeting. Same data, different doors.
